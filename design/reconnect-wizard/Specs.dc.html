Status — what the row wants from you

Six, not four
Found matched Strong match, applied without asking. Auditable, and rejectable.
Needs review ambiguous More than one candidate, or one that is not close enough to trust.
Refuted refuted A candidate was found and then withdrawn, because the duration contradicts. In the queue by default.
Re-encoded format Same track, different container. The file was replaced rather than moved.
Left missing rejected You looked and said no. Reversible until the write.
Not found no_match Nothing plausible was found. Read-only unless you scan more folders.

Colour says what the row wants; icon and word say which question it is asking. The three review statuses share one hue on purpose — yellow means a decision is outstanding — and are told apart by a distinct icon silhouette and the written word, both carried in the first column. Refuted and re-encoded therefore add no colour, so the measured palette opposite stands unchanged rather than needing to be simulated again.

Re-encodes are found, not asked for

A re-encode replaces the file rather than moving it, so every tier keying on the name as written stops matching and the track reads as gone. The two tiers that strip the container sit at loose and filename, levelled on the evidence they carry rather than on the outcome anyone wants: one is strictly weaker than a two-folder path suffix, which sits at loose on its own measurement.

The wizard runs those tiers and surfaces the result as review. It does not require the operator to know that a --match-confidence flag exists, and it does not promote the tiers to strict to dodge the question. Duration still refutes at loose, which is what keeps them safe; size does not, because the same track legitimately runs 0.23× to 49× across formats.

App header — brand, divider, section tabs

Every screen

The header reads left to right as the brand mark, then the .bar divider, then the section tab strip. The strip carries one tab per operation, Reconstruct playlists leftmost and Reconnect wizard second, and it is the whole of the header: the brand, the divider and the strip.

traktor-nml-tool
Reconstruct playlists Reconnect wizard
  • A tab is an anchor, and its href is that operation’s route. / carries Reconstruct playlists and /reconnect carries Reconnect wizard, so following a tab is a page load and each operation keeps the address it is reachable by.
  • The selected tab takes the .st.now treatment the wizard artboard paints: the #22262A ground, an inset 1px #3C4248 border, and #E8EBED ink at weight 600.
  • An unselected tab is #8E979E ink on the header’s own #17191C ground, with no background of its own. Nothing else separates the two states, so the treatment carries ground, border, ink and weight together.
  • The selected tab carries aria-current="page", and exactly one tab carries it per page — the tab naming the route that page answers. Two tabs carrying it, or none, is a defect.
  • The header names the screen through the selected tab and carries no .task element. The strip already names both operations and marks which one is open, so a second name beside it would come from a source that can disagree with the first with no rule saying which wins. .task and .rail belong to the wizard artboard’s own screen.

Confidence — four levels, three channels

Strong strict Artist, title and length all agree. Applied without asking you.
Good normal One field differs — often a remaster or a different edit. Shown to you.
Weak loose Only the title matches, or several files match equally well. Always shown.
None no_match Nothing plausible found. Stays missing unless you scan more folders.

Never colour alone

Every state carries three independent signals, so removing any one still leaves it readable:

  • Shape — filled versus outlined dots for confidence; a distinct icon silhouette per status (tick, ringed dot, cross, dashed ring).
  • Word — the status is written out in every row. No row relies on a swatch.
  • Position — status is always the first column, decision always the last.

The dot meter is counted, not measured: three discrete dots read correctly in greyscale, at 200% zoom, and to anyone who cannot separate the yellow and the green.

The palette is measured, not chosen by eye. Hues follow Okabe–Ito's Color Universal Design set, lightened for a dark UI, and each status pair was simulated for protanopia, deuteranopia and tritanopia. The worst separation between any two status colours, under any of the three, is ΔE 22.6 — above the 20 threshold for comfortable distinction.

Action never shares a hue with caution. That collision — a button that reads as a warning — is why the accent moved off amber. Action appears only as a filled control; caution only as text and icon.

Every button is filled with Action. The label is the ground, #0F1113, which reads 8.2:1 on the blue, and it is set in the case it is written in, never forced to capitals. A disabled button takes the off colours - #15171A ground, #2A2E32 border, #8A9299 label - so it never reads as a blue control waiting to be pressed. A button whose colour is its meaning keeps it: accept in Found, reject in Not found, and the destructive cancel in its warm tint. With every button blue, colour does not set a screen’s primary action apart; weight does, 600 against the 500 every other button carries.

Accept and reject

Nothing is destructive
UNDECIDEDwhere every reviewable track starts
A accept → ACCEPTED
R reject → LEFT MISSING
U from either → back to UNDECIDED
  • Picking a candidate is not accepting. 1–9 changes which file is proposed; the row stays undecided until you accept it.
  • A refuted candidate accepts like any other. No confirmation on top, no second dialog: the detail panel already names the contradicting field and quantifies it, and a click the operator learns to dismiss teaches nothing.
  • Automatic matches can be rejected too. A wrong Strong match is demoted to left-missing like any other.
  • Undecided is a valid ending. It is not an error, it does not block the write, and it leaves the track exactly as it is today.
  • Decisions survive re-filtering and searching, and are only frozen when the collection is written.

Unresolved, spelled out

Three different things end up unresolved, and the wizard never blurs them together:

  • Rejected — you looked and said no.
  • Undecided — you did not get to it.
  • Not found — there was nothing to decide.

Two resolutions are counted apart from an ordinary accept for the same reason, because they are not the same decision: accepting a refuted candidate overrides a positive contradiction, and accepting a re-encode changes the track’s format in Traktor. Each gets its own line before the write.

All three are counted separately in the pre-write summary, written to the CSV with their reason, and described the same way: left exactly as it is today. None of them is presented as a failure.

Splice conflicts — Reconstruct playlists

One row per track

A reconstruction reads a base collection and one or more source collections. Where they hold the same track with different tags, the run stops and asks. Every conflicting track gets one row, and the operator picks the collection whose values win.

  • One control per distinct answer. The row carries a control for each set of values the track is held with, labelled with the collections supplying it and those values; the chosen one carries the selected outline. There is no third “merge” state and no free-text edit.
  • Above the rows: a bulk strip and a count. The strip reads All base followed by one action per source collection, each labelled by the shortest trailing run of path segments that tells that source apart from the others — the file name where nothing collides, the file name plus as many parent folders as it takes otherwise, and the whole path where nothing shorter separates them. A bulk action settles every undecided row its own collection holds the track in and leaves the rest undecided. The count reads 14 of 212 still undecided, so the operator knows what is left without scrolling.
  • Rows are hand-built, one per track, in the same 32px-tall control rhythm as the review table, so the arrow keys the review table binds stay available over this table too.
  • Picks survive a re-preview that leaves the answers alone. Changing the output path keeps every pick already made; they live for the length of the session. A pick whose track is held by a different set of collections, or offered a different set of answers, returns to undecided and is asked again, because it was made about answers the run is not offering.
The write refuses while any track is undecided. The refusal reads The preview refused: 14 conflict(s) still to decide. Choose a collection for each row above, then run Preview again. — naming the count and the control that clears it rather than the bare token the run reports. Writing a collection with a guessed winner would be plausible and wrong, so no output is offered until every row names a collection.

Accessibility rules

  • Focus ring 2px solid on the light foreground, 2px offset, on every focusable control. Never removed, never colour-only — it changes the outline, not the fill.
  • Announcements use a polite live region: progress at most every 2 seconds ("4,212 of 12,542"), and each decision as it happens ("Bar A Thym accepted — 458 of 1,238 done").
  • Errors and completion are assertive, and name the file consequence in the first sentence.
  • Dialogs trap focus, open on the safe button, and return focus to whatever opened them.
  • Controls are 32px tall with 8px between them — every button on every screen, including the small ones in table rows. The whole row is the click target, not just its buttons.
  • Reduced motion is respected: the spinner becomes a static mark, the progress bar stops animating, counts still update.
  • Text reflows at 200% zoom down to 1024px wide — the detail panel drops below the table rather than clipping.
  • No text below 11px, and no body copy below 12px. Secondary text meets 4.5:1 against its own surface, not against the page.
Scope fence. Everything here serves one sentence: my playlists are broken — they still exist, but their tracks will not load, because the files moved. Repair works by repointing the collection entries those playlists reference; names, order and history are never touched.

A deleted playlist is a different job. Rebuilding one from a written tracklist is something the tool already does — build-playlist — but it needs a list to work from, has its own review model, and is not in Phase 1. When it arrives it is its own entry point, not a branch of this one. Merging collections, splitting them and comparing two collections are absent for the same reason.
