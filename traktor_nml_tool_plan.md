# Implementation Plan: Generalized Path Reconnection + Splice/Split for `traktor_nml_tool.py`

## Status

- **Phase 1 (disk-scan path reconnection): ready to implement.** One-to-one assignment invariant, old-side fingerprint gating, explicit VOLUME/VOLUMEID mapping, destination-collision handling, dry-run parity, and the byte-masked-diff acceptance criteria are all specified — see Phase 1 below, unchanged from the prior revision.
- **Phase 2 (splice/split): the three previously outstanding items are now resolved, not merely planned:**
  1. *Playlist-import algorithm* — fully specified as six concrete steps in "Playlist-import algorithm for splice" below (qualifying nodes, copy/insert target, PRIMARYKEY retention/redirection, deterministic renaming with UUID regeneration, abort-on-unresolved-reference, SORTING_INFO handling).
  2. *Real NML playlist hierarchy/count attributes* — verified directly against the local corpus (`collection_textual_patch_test.nml`, 6,412 real collection entries), not assumed. See "Schema discovery" below for the exact tag/attribute names found (`PLAYLISTS`/`NODE TYPE="FOLDER"`/`SUBNODES COUNT`/`NODE TYPE="PLAYLIST"`/`PLAYLIST ENTRIES UUID`/`PRIMARYKEY TYPE+KEY`), plus one previously-unknown section (`INDEXING`/`SORTING_INFO`) discovered in the process and now accounted for.
  3. *Raw fragment preservation vs. normalized serialization* — decided explicitly: span transplantation (byte-exact copying from source) is now the v1 default for every unmodified fragment; `ET.tostring()` serialization is retained only as a labeled fallback for fragments that are actually modified (renames, redirects). See "Textual-fidelity policy" below, including the acceptance test that states precisely which bytes may change.

  Phase 2 is accordingly also ready to implement, on the same explicit-decision basis as Phase 1 — the schema-discovery and fidelity-decision prerequisites this feedback asked for are complete, not outstanding.

2. **Unify `_process_non_collection_rule_entries` and `_process_non_collection_compare_entries`** into one cascade helper parameterized by a `resolve(old_key_or_loc) -> Optional[NewTarget]` callable — verified line-by-line (793-850 vs 852-888) to be structurally identical modulo the resolution function.
3. **Unify `cmd_rewrite`/`cmd_rewrite_from_collection_compare`'s** read-bytes/HAS_LXML-branch/patch-collect/write skeleton into one `write_nml_safely` helper, scoped strictly to today's 1-in/1-out shape. Expect this helper to need a second revision once Phase 2 lands (splice is N-in/1-out, split is 1-in/N-out) — that's a planned future touch-point, not a sign Phase 0 was mis-scoped.

Validate each extraction by diffing `rewrite`/`rewrite-from-collection-compare` output bytes against pre-refactor output — must be identical.

## Phase 1 — Generalized disk-scan path reconnection

**Hard invariant, unchanged from the existing tool**: reconnection writes only ever change the intended `LOCATION` and `PRIMARYKEY` attribute values via the existing `apply_text_patches` mechanism. Every other byte of the source file — whitespace, attribute order, unrelated elements — is preserved exactly. Nothing in this phase introduces a second write path; disk-scan reconnection is a new *candidate source* feeding the same attribute-patch pipeline `rewrite-from-collection-compare` already uses.

New subcommand pair following the existing `scan-compare-candidates` → `rewrite-from-collection-compare` naming pattern (e.g. `scan-reconnect-candidates` + `rewrite-from-reconnect`):

- `DiskCandidate`/`TagReadResult` (mutagen-based) + `index_scan_roots()` walking repeatable `--scan-root` paths, deduped by resolved absolute path.
- `disk_candidate_to_entry_record()` wraps each readable file as an `EntryRecord` with `entry=None`, populated from tags (artist/title/album/filesize/playtime/bitrate/file_name). AUDIO_ID can never be populated this way — it's a Traktor-internal fingerprint, not a standard tag — so disk-side records structurally never hit that top match tier.
- Feed disk records as the `new_records` side of the **existing, unmodified** `match_records`/`record_keys` cascade. Reuse `_collect_compare_patches` + the (Phase-0-unified) cascade helper + `apply_text_patches`/`_apply_and_write` completely unchanged for writing — this is the load-bearing reuse insight: no modification to the matching or write core is required, only additive code.
- **One-to-one assignment invariant (required, not optional)**: no single disk candidate may be assigned as the rewrite target for more than one old collection track. After `match_records` produces its old→new mapping, add an explicit post-pass that inverts the mapping (new-candidate → list of old tracks assigned to it) and treats any candidate with more than one assignment as a **destination collision** — all old tracks mapped to that candidate are pulled out of the mapping, reclassified as `ambiguous` (not `matched`), and excluded from rewrite entirely, regardless of which match tier produced the collision. This is a new check because `match_records`'s existing ambiguity detection only looks at *source*-side ambiguity (multiple candidates for one old track); it does not currently detect *destination*-side collisions (multiple old tracks converging on one candidate), which is a distinct failure mode — e.g. two old collection entries that both plausibly matched the same physical file. Reported as a new `stats["destination_collisions"]` counter and included in the CSV ambiguous-report export.
- New logic genuinely required: `location_from_disk_path()` (inverse of the Traktor-DIR encoding) plus **explicit target VOLUME/VOLUMEID identity**. Reconnection must set both `VOLUME` and `VOLUMEID` on every rewritten `LOCATION` — never leave either unset or silently defaulted. VOLUME/VOLUMEID may be inferred from an existing collection entry whose decoded path is a *prefix match* of the scan root **only when that inference is unambiguous** (exactly one distinct VOLUME/VOLUMEID pair among all existing entries under that prefix); if the prefix is absent, ambiguous (multiple distinct VOLUME/VOLUMEID pairs observed under it), or the scan root doesn't correspond to any path recorded in the old collection at all (the common case after a full drive/mount change), inference is refused and an explicit `--volume-map SCAN_ROOT VOLUME[:VOLUMEID]` flag is **required** for that root — the tool must error out (or skip that root's candidates, `--dry-run`-reported) rather than guess. This closes the gap where "infer from old collection paths after a move" was previously offered as a silent fallback: post-move, old paths are exactly the thing that's unreliable, so inference is now an opportunistic shortcut only under a verified-unambiguous condition, never a fallback of last resort.
- Performance/safety at scale: a persistent tag-read cache keyed by `(path, size, mtime)` (documented limitation: doesn't recognize a renamed-but-identical file), incremental progress output, and incremental cache flushing so an interrupted scan loses at most its last batch.
- **Scope decision, revised: fingerprinting is opportunistic and old-side-gated, not a v1 blocking requirement.** The originally confirmed "tags + fingerprinting in v1" scope has a design gap: a fingerprint computed only from scanned (new) candidates has nothing to compare against, because the **old** collection's original media is exactly the thing reconnection assumes may be unreachable (that's why paths need reconnecting). Traktor's NML does not store an audio fingerprint for old entries — `AUDIO_ID` is Traktor's own internal identifier, not a portable acoustic fingerprint, and there is no other in-file field usable as one. This means fingerprint matching can only ever compare a *new* candidate's fingerprint against an *old* fingerprint computed from the *original file*, which requires that original file to still be physically reachable somewhere.
  - **Old-side fingerprint source, defined**: fingerprinting is attempted for an old track **only when its recorded old `LOCATION` path is still resolvable on disk at scan time** (i.e., the file wasn't actually moved, or a copy still exists at the old path — e.g. a partial migration, or the user scanning both old and new drives). When resolvable, the old track's fingerprint is computed once, cached, and used as a top-tier match key (above tag-based keys, below nothing — it is the strongest available signal when both sides have it). When the old path is *not* resolvable (the common case this whole feature exists for), no old-side fingerprint exists, and fingerprint matching is **silently absent for that track**, falling through to the tag-based cascade — not an error, since this is the expected common case, but explicitly counted in stats (`fingerprint_unavailable_old_side=N`) so it's visible in output, not silently invisible.
  - **Dependencies**: `chromaprint` (native binary, via `pyacoustid` or direct `fpcalc` subprocess invocation) — a heavier, non-pure-Python dependency than `mutagen`, gated behind its own import/binary-availability guard (matching the `HAS_LXML` pattern): if `fpcalc` is not on `PATH` or `pyacoustid` is not installed, the tool runs with tag-only matching and prints one clear warning, not a hard failure.
  - **Offline behavior**: fingerprint computation itself (via `chromaprint`/`fpcalc`) is fully local/offline — no network calls. If a user additionally wants AcoustID's online database lookup (matching a fingerprint against MusicBrainz metadata), that is explicitly **out of scope for v1** — this tool only ever compares two locally-computed fingerprints against each other (old-side vs. new-side), never queries an external service, consistent with the tool's existing zero-network posture.
  - **Cache semantics**: fingerprint results are cached in the same persistent cache as tag reads, keyed by `(path, size, mtime)`, storing a nullable fingerprint field alongside tag data — a cache entry with `fingerprint=None` records "we tried and the path was unreadable/tool unavailable at that time," distinct from "not yet attempted," so re-runs don't redundantly retry known-failed reads unless `--refresh-cache` is passed.
- **CLI/flag design (confirmed): unify into one enum.** Introduce a shared `--match-confidence {strict,loose,filename}`-style enum used by both the new disk-scan command and the existing `preview-compare`/`rewrite-from-collection-compare` commands. `--allow-artist-title-only` becomes a backward-compatible alias for the `loose` value on those existing commands (parsed and mapped internally, still accepted on the command line) rather than being replaced outright — this is a small, deliberate migration touching existing commands, not just new-command scope.
- Ambiguous/unmatched cases extend the existing `match_records` stats and get CSV export via the existing `location_rows`/`csv.DictWriter` pattern — never silently resolved.

**Phase 1 acceptance criteria**:
- No output file ever assigns two old collection tracks to the same disk candidate's LOCATION (destination-collision test suite, see Testing & Rollout Plan below, is green).
- No output file ever contains a `VOLUME` or `VOLUMEID` value that was not either copied from an existing collection entry under a verified-unambiguous prefix or supplied via `--volume-map`.
- Every rewritten attribute is a `LOCATION` or `PRIMARYKEY` value; a byte-diff of the output against the input, with all matched-and-rewritten attribute values masked out, is empty.
- `--dry-run` output and the post-write result agree exactly on which tracks were matched, ambiguous, destination-collided, or unmatched.

## Phase 2 — Splice and split (independent command surface, ships second)

### Schema discovery (completed against the local NML corpus)

Confirmed directly by inspecting `collection_textual_patch_test.nml` (a real, 6,412-entry, 79k-line collection) — this closes the schema-verification prerequisite; no items below remain "unverified, needs a sample."

- **Root/collection**: `<NML VERSION="20"><HEAD .../></NML>` wraps everything. `<COLLECTION ENTRIES="6412">` — **the count attribute is confirmed to be `ENTRIES`**, matching what the existing tool already assumes.
- **Playlist hierarchy**: a single `<PLAYLISTS>` section (top-level sibling of `COLLECTION`) contains one root `<NODE TYPE="FOLDER" NAME="$ROOT">`. Every `FOLDER` node wraps a `<SUBNODES COUNT="N">` element containing child `<NODE>` elements (nesting observed to at least 4 levels deep, e.g. `$ROOT` → `00_onDrive` → `08_2026` → `07_Jul` → a playlist). Every `PLAYLIST` node is `<NODE TYPE="PLAYLIST" NAME="...">` wrapping exactly one `<PLAYLIST ENTRIES="N" TYPE="LIST" UUID="...">`. **Two count attributes exist and must both be recalculated on any structural change**: `SUBNODES COUNT="N"` (child-node count on a folder) and `PLAYLIST ENTRIES="N"` (track count on a playlist).
- **Playlist entries**: `<PLAYLIST ...><ENTRY><PRIMARYKEY TYPE="TRACK"|"STEM" KEY="..."></PRIMARYKEY></ENTRY>...</PLAYLIST>`, or self-closed `<PLAYLIST ENTRIES="0" ...></PLAYLIST>` with no `ENTRY` children when empty (confirmed present in real data — Traktor itself is comfortable writing empty playlists, though this plan's split still chooses to omit them by default per the earlier design). **`PRIMARYKEY` carries a `TYPE` attribute** (`TRACK` or `STEM`) in addition to `KEY` — not previously documented in this plan — and must be preserved verbatim, never dropped, when copying or redirecting a reference.
- **Playlist identifier**: every `PLAYLIST` element carries a `UUID` attribute (32-char hex). This is the "required identifier" that splice's collision policy must address (see below).
- **History, resolved**: the real corpus contains **zero** occurrences of any `HISTORY`-named tag. The only history-adjacent-looking section is `<SETS ENTRIES="N"><SET TITLE="..." QUANT_VALUE=... QUANT_STATE=...><LOCATION .../></SET></SETS>` — this is Traktor's **Remix Sets** feature (saved Remix Deck setups), unrelated to playback-session history logs. **Conclusion: this NML schema version (VERSION="20", Traktor Pro 4) does not appear to have a session-history container at all.** The earlier "defer history, needs a sample" open item is now closed: there is no history schema to defer — `SETS`/`SET` is out of scope for splice/split v1 for the same reason (it's an unrelated feature, not curated track playlists), and should be treated as untouched/passed-through data, not merged or split.
- **Newly discovered: `INDEXING`/`SORTING_INFO`**. Immediately after `</PLAYLISTS>`, a top-level `<INDEXING>` section lists `<SORTING_INFO PATH="...">`  entries — one per playlist — each keyed by a **backslash-separated path string** (e.g. `PATH="otherDJs\mvp\2023_matt\new midtempo"`, distinct from the `/:`-encoded style used elsewhere in the file) and containing `<CRITERIA ATTRIBUTE="N" DIRECTION="0|1">` (sort column/direction). This was not identified in the original design pass. **It directly affects splice's renaming policy**: renaming or relocating a playlist without updating its matching `SORTING_INFO PATH` orphans that sort setting (harmless — Traktor will just use a default sort — but silently loses the user's chosen sort order, which the "never silently discard track state" principle should extend to). Splice/split v1 must therefore either update `SORTING_INFO PATH` to match a renamed/relocated playlist, or explicitly drop it and report that it did so — never leave a stale, silently-orphaned entry unremarked.

### Playlist-import algorithm for splice

Given the confirmed schema above, splice's playlist handling is now fully specified:

1. **Which source `PLAYLIST` nodes qualify for import**: every `NODE TYPE="PLAYLIST"` reachable anywhere in a non-base input's `PLAYLISTS` tree qualifies — v1 does not filter by folder location (that's consistent with the Phase 2 scope boundary: folder nesting itself is not preserved, so a non-base playlist's origin-folder position is not a qualification criterion, only its name/UUID identity is).
2. **How non-colliding playlists are copied and where they are inserted**: a non-base playlist whose `NAME` does not match any base playlist's `NAME` is serialized whole (`<NODE TYPE="PLAYLIST" NAME="...">...</NODE>`, its own `<PLAYLIST>`/`<ENTRY>`/`<PRIMARYKEY>` subtree intact) and inserted as a new child of the base's root `<NODE TYPE="FOLDER" NAME="$ROOT">`'s `<SUBNODES>` — i.e., flattened one level into the base's top-level playlist list, not reconstructed into whatever nested folder it originally lived in (consistent with "folder nesting is not preserved" in the scope boundary). The base's own `SUBNODES COUNT` is incremented accordingly.
3. **How source `PRIMARYKEY` entries are retained or redirected**: a copied playlist's `PRIMARYKEY` entries are retained verbatim (same `TYPE` and `KEY`) if the referenced source track was **not** involved in an identity conflict (i.e., it's uniquely present, or it was the accepted winner under `--on-conflict`); if the referenced track lost an identity conflict, its `PRIMARYKEY` is rewritten to the winning entry's key via the existing `old_to_new_key` + cascade-redirect idiom — identical mechanism to Phase 1's playlist-reference redirection, just driven by splice's conflict resolution instead of a path rewrite.
4. **How same-name playlists are deterministically renamed**: when a non-base playlist's `NAME` collides with an existing (base or already-imported) playlist name, the imported copy is renamed `"<name> (2)"`, incrementing (`(3)`, `(4)`, ...) until unique; its `UUID` attribute is regenerated (a fresh random 32-char hex) rather than reused, since the schema confirms `UUID` exists as a real per-playlist identifier and copying it verbatim would create a duplicate UUID within the same file — this is new, corpus-confirmed handling that supersedes the earlier "UUID collisions are out of scope" statement now that UUID is known to exist and matter.
5. **How unresolved playlist references abort or are reported**: if, after conflict resolution, a copied playlist's `PRIMARYKEY` cannot be resolved to any surviving entry in the merged `COLLECTION` (should not occur given step 3's redirection, but is checked as a hard invariant, not assumed), splice aborts the entire write (zero-write-on-error, consistent with Phase 1's convention) and reports every unresolved reference by playlist name and `KEY` — never silently drops the reference or writes a dangling `PRIMARYKEY`.
6. **`SORTING_INFO` handling**: for each imported/renamed playlist, its corresponding `SORTING_INFO` entry (if the source file has one for that playlist's original path) is copied into the base's `INDEXING` section with `PATH` rewritten to reflect the new flattened location and any rename from step 4; if no `SORTING_INFO` entry existed for that playlist, none is fabricated.

### Textual-fidelity policy (revised: span transplantation is the default; serialization is an explicit fallback)

The original plan defaulted to `ET.tostring()`-serializing every non-base fragment. **Revised**: prefer raw XML **span transplantation** wherever feasible, consistent with the tool's existing byte-preservation ethos:

- For each non-base `ENTRY` (in `COLLECTION`) and `NODE`/`PLAYLIST` subtree (in `PLAYLISTS`) being imported unchanged, locate its exact byte span in the **source file's raw text** (via the same `_find_opening_tag_end`-style scanning already used for `LOCATION`/`PRIMARYKEY`, generalized to find matching closing tags) and copy those bytes verbatim into the output. This preserves the source's original attribute order, whitespace, and escaping exactly for every transplanted fragment — true byte-for-byte fidelity, not just structural equivalence.
- **`ElementTree`/lxml serialization (`ET.tostring()`) is retained only as an explicit, clearly-labeled lower-fidelity fallback**, used only when a fragment must actually be *modified* before insertion (e.g., a renamed playlist per step 4 above, or a `PRIMARYKEY` redirected per step 3) — in which case only that specific fragment is re-serialized; every unmodified fragment still goes through span transplantation.
- **Acceptance test for this item**: run splice against two fixture inputs where every playlist name is unique (no rename, no redirect needed) and assert the output is **byte-identical concatenation** of exact source spans plus only the count-attribute patches — i.e., a diff of the output against "base file bytes + transplanted-verbatim non-base spans" is empty. A second test introduces exactly one name collision and one conflict-redirect, and asserts that **only** the renamed playlist's `NODE`/`PLAYLIST` opening tag + regenerated UUID, and **only** the redirected `PRIMARYKEY`'s `KEY` attribute, differ from a pure span-transplant baseline — every other transplanted byte, including all other playlists and all other entries, remains byte-identical. This precisely states which bytes may change and which must not.

### Fingerprint comparison semantics for splice's identity/dedup

(Splice reuses the `record_keys` tier ordering per the original design; this closes the previously unspecified "how do two fingerprints actually get compared" gap, and applies equally to Phase 1's old-side-gated fingerprint tier.)

- **Duration tolerance**: two fingerprints are only compared if their source files' durations (from tag/`.info.length` reads, already collected) agree within **±1.0 second** — chosen because chromaprint fingerprints are computed over a fixed-length audio window and are not meaningfully comparable across tracks with materially different lengths; a tighter tolerance risks false negatives from rounding/container-overhead differences already noted as a risk elsewhere in this plan, a looser one risks comparing unrelated tracks.
- **Match threshold**: fingerprint comparison uses chromaprint's own raw fingerprint compression correlation (via `pyacoustid.compare_fingerprints` or equivalent), which returns a similarity score in `[0.0, 1.0]`; a pair is considered a fingerprint match **only above 0.95 similarity** — a conservative, high-precision threshold chosen because a false-positive fingerprint match would (per the one-to-one assignment invariant) silently redirect a track's playlist references to the wrong physical file. Scores between 0.80 and 0.95 are logged as `fingerprint_near_match` (visible in the ambiguous/unmatched CSV export) but **not** treated as a match — surfaced for human review, never auto-accepted.
- **Eligibility gate, stated explicitly**: a fingerprint comparison is only ever eligible to drive a rewrite decision when (a) both sides have a successfully computed fingerprint (old-side reachability per Phase 1's gating, or both-sides-present for splice's dedup), (b) duration tolerance is satisfied, and (c) similarity exceeds the 0.95 threshold. Failing any of the three, the fingerprint tier contributes nothing and matching falls through to the next tier in the existing cascade — fingerprinting can only ever narrow ambiguity or add confidence, never force a match that the tag-based cascade wouldn't otherwise support at a lower confidence tier.

### Acceptance criteria

- Splice never writes output when an unresolved (non-`--on-conflict`-overridden) metadata conflict exists; every conflict, resolved or not, appears in the persistent conflict report.
- No splice/split output's `COLLECTION ENTRIES`, `PLAYLIST ENTRIES`, or `SUBNODES COUNT` attribute disagrees with its actual child-entry/child-node count.
- No split output contains a `PLAYLIST` entry referencing a track absent from that output's own `COLLECTION` (referential integrity), except under an explicit, logged `--dangling-policy pull-in` choice.
- Splice's playlist name-collision renaming is deterministic, always regenerates a fresh UUID for the renamed copy, and never silently drops or merges a same-named non-base playlist's entries into an existing base playlist.
- No unresolved `PRIMARYKEY` reference (a copied playlist entry pointing at a track absent from the final merged `COLLECTION`) ever reaches the output file — verified as a hard pre-write invariant, not assumed from step 3's redirection logic alone.
- Span-transplantation acceptance tests (above) pass: an all-unique-names splice run is byte-identical to a pure span-concatenation baseline; a rename+redirect run differs from that baseline only in the specifically renamed/redirected bytes.
- Every `SORTING_INFO` entry in the output either corresponds to a still-valid playlist path in that output's `PLAYLISTS` tree, or was explicitly dropped and reported — never silently orphaned.

**Split**: filter scope, dangling-reference policy, and count recalculation are unchanged from the previous revision of this plan — see below, now cross-referenced against the confirmed schema.

- **Filter scope (confirmed, simplified): named playlist(s) only** — each `--group OUTPUT PLAYLIST [PLAYLIST ...]` names one or more existing playlists (matched by `NAME`, now confirmed to be the sole naming attribute — there is no separate playlist-path attribute distinct from folder nesting, which is out of scope) whose entries go to that output.
- Dangling-reference policy: default `exclude` (drop non-selected refs — always yields a valid file, never duplicates audio); `pull-in` (opt-in, documented divergence risk); `fail` (strict validation). A playlist reduced to zero kept entries is omitted entirely (`playlist_dropped=<name>`); partial retention is reported as `playlist_partial=<name>:<kept>/<total>`.
- Write mechanism: span transplantation (see Textual-fidelity policy above) — split is **fully** byte-preserving for every kept fragment, since nothing is foreign and nothing needs renaming, only `COLLECTION ENTRIES`/`PLAYLIST ENTRIES`/`SUBNODES COUNT` are patched attribute values.
- `SETS`/`SET` (Remix Sets) content is passed through untouched into every split output that retains the base file's structure, since it's unrelated to playlist membership — not filtered, not duplicated-with-modification, simply carried as-is.

## Why this order

Phase 1 reuses the existing compare-based matching and write path essentially unchanged — it's additive, not a modification of shared internals, so it doesn't strictly require Phase 0 first. Phase 2 is architecturally harder: both splice and split need a genuinely new structural write primitive (insert/remove whole elements) since the existing `apply_text_patches` is attribute-substitution only — this was independently arrived at by reasoning about the write mechanism and reasoning about existing code risk, which is a meaningful cross-check. Building Phase 1 first exercises and hardens the shared write path against one new consumer before Phase 2 asks it to support a fundamentally different (multi-document) shape.

## Testing & Rollout Plan (applies to both phases)

**Fixture corpus** — synthetic and/or anonymized real NML files covering:
- Moved tracks (path changed, file otherwise identical).
- Renamed tracks (filename changed, tags/content identical).
- Duplicate/near-duplicate tracks (same track ripped twice, different bitrate/container — must exercise the one-to-one assignment invariant and destination-collision reporting).
- STEM files (Traktor's multi-track stem format) — verify tag reading and fingerprinting behave sanely on this format rather than being silently skipped or misread.
- Entity-encoded / escaped characters in ARTIST/TITLE/paths (e.g. `&amp;`, non-ASCII filenames) — verify `apply_text_patches`' XML-escaping round-trips correctly.

**Process gates, all required before a run is considered safe**:
- `--dry-run` output and CSV ambiguous/unmatched/conflict reports must be reviewed before any real write — this is a workflow requirement of the tool's design, not just a suggestion, and should be called out in `--help`/docs as the expected usage pattern.
- **Zero-write-on-ambiguity/error**: any unresolved ambiguity, destination collision, unresolved splice conflict, or mid-run error aborts the entire write for that output file — no partial-file writes. Verified by a test that injects a failure partway through patch collection and asserts the output file is either absent or byte-identical to a prior successful run (never a half-patched file).
- **Cache interruption coverage**: a test that kills the scan process mid-run (simulated via interrupting the cache-writing loop) and asserts a subsequent run resumes correctly — no duplicate work, no lost already-cached entries, and the candidate pool from a resumed run matches a non-interrupted run over the same inputs.
- **Generated-file XML validation**: every output file must parse successfully via both the lxml and stdlib parsers used elsewhere in the tool, and must pass a schema/structure sanity check (COLLECTION count matches child count, every PRIMARYKEY resolves within the file, every PLAYLIST entry resolves to a COLLECTION entry) before being considered a valid test pass.
- **Traktor import/open validation**: a manual (documented, not automated in CI) verification step — open each generated test-fixture output in an actual Traktor installation and confirm it imports/loads without error or data loss, before the feature is considered release-ready. This is the final gate no automated test can substitute for.
- **Rollback to untouched originals**: every write operation's input file must remain completely untouched (the tool already refuses `output == input`); the rollout plan requires that test/rollout runs always operate on a copy, with the original preserved and diffed against post-run to confirm zero incidental modification.

## Decisions confirmed with the user
- **Phase 1 matching signal**: tags (mutagen) as the primary v1 signal; acoustic fingerprinting included but revised to be **opportunistic and old-side-gated** (only used when the old track's original path is still reachable to compute a comparison fingerprint), not a blocking v1 requirement — see the resolved design gap above. (Phase 1 is otherwise unchanged and considered sound: old-side fingerprint gating, VOLUME/VOLUMEID mapping, destination-collision handling, dry-run parity, and byte-masked diff acceptance criteria all stand as previously specified.)
- **CLI flag design**: unify `--match-confidence` as a shared enum across old and new commands; `--allow-artist-title-only` becomes a backward-compatible alias.
- **Split filter scope**: simplified to named-playlist selection only (no folder/artist/date/entry-list clauses in v1); Phase 2 as a whole is scoped to flat playlist-entry merge/subset, not full playlist-tree preservation (see Phase 2 scope boundary above).
- **History entries**: resolved, not merely deferred — the confirmed schema (see Schema discovery) shows no `HISTORY` container exists in this NML version; `SETS`/`SET` (Remix Sets) is a distinct, unrelated feature and is passed through untouched by splice/split.
- **Splice conflict policy**: `fail`-by-default with a persistent conflict report always written; `keep-first`/`keep-last` available only via explicit `--on-conflict`.
- **Reconnection VOLUME/VOLUMEID**: always set explicitly; inference from old collection paths is allowed only when unambiguous, never as a silent fallback after a full drive/mount change.
- **Splice write mechanism**: revised from "serialize every non-base fragment" to span-transplantation-by-default, with `ET.tostring()` serialization retained only as an explicit fallback for fragments that are actually modified (renames, redirects).
- **Fingerprint comparison semantics**: ±1.0s duration tolerance, 0.95 similarity match threshold, 0.80–0.95 logged as near-match-for-review-only — specified before fingerprints are eligible to drive any rewrite.
